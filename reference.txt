Problem Statement: Traditional machine learning workflows require significant human expertise for data analysis, preprocessing, model selection, and hyperparameter tuning. While existing AutoML systems automate parts of this process, they rely largely on blind or heuristic searches and lack reasoning, adaptability, and explainability. 

Consequently, these systems often incur high computational costs, provide limited insight into their decisions, and still require human intervention to improve performance. This highlights the need for an autonomous intelligent system that can analyze raw datasets, reason about suitable machine learning strategies, and iteratively refine decisions in a human-like manner.

The proposed methodology is divided into parts - 

Phase - 1: Initialization
Step 1: User Intent Parsing - 
The LLM receives the user's instruction and raw dataset and classifies user instruction into one of four states before any data processing begins.
In-scope: maps to classification or regression. The LLM extracts a task config: plain-English goal, task type, user constraints, and target variable if identifiable from the instruction. If the target is unclear it is marked deferred and resolved in Step 5. A plain-English confirmation is shown to the user.
Ambiguous: could be in-scope but needs clarification. The system asks exactly one plain-English question to resolve it before proceeding.
Out of scope: maps to an unsupported task. The system stops, explains what it is designed for without ML terminology, and suggests a possible in-scope reframing if one exists. No processing begins unless the user restates their goal as in-scope.
Unrecognizable: cannot be mapped to any data task. The system stops and asks one clarifying question.
Step 2: Input validation - 
Pure code. Verifies the file can be opened, contains at least one row and column, is within size limits, and is a supported format (CSV, Excel, JSON, Parquet). On failure a plain-English error is returned and the session stops.
Step 3: Initialize agent memory - 
Runs immediately after input validation passes. Creates four components: task config (partially populated, deferred fields marked), dataset profile (empty, populated in Step 4), decisions log (append-only timestamped record of every LLM decision and rationale), and dataset state pointer (pointing to the raw file). Memory persists through all subsequent phases.
Step 4: Dataset profiling snapshot -
Pure code. Computes row and column count, inferred data types, null percentage per column, cardinality per column, basic distribution statistics for numeric columns, and value counts for low-cardinality categorical columns. If the target column is already known its distribution is included. Written to memory. Never shown raw to the user
Step 5: Task classification agent - 
The LLM reads the dataset profile and task config. If the target column was deferred it is now inferred from the profile — the LLM looks for columns whose name and distribution match the task type, proposes the inferred target to the user, and confirms before proceeding if confidence is low.
The LLM then selects a default evaluation metric: F1 for balanced binary classification, AUC-ROC for imbalanced binary, macro F1 for multiclass, RMSE for regression, MAE when significant outliers are present. The choice is explained to the user in plain English. All decisions are written to the decisions log.
Output is a fully populated task config — task type, confirmed target column, evaluation metric, and user constraints — which serves as the single source of truth for all subsequent phases.
Phase - 2: Planning (Mode 1: Preprocessing Plan)
Single step — preprocessing plan
The planning agent reads the task config and dataset profile and produces a lightweight preprocessing plan in one LLM call. It identifies likely challenges: columns with high null rates, categorical columns needing encoding, skewed numeric distributions, and potential leakage risks such as columns whose cardinality equals the row count. It reasons about whether feature engineering is likely to be worthwhile given dataset size and feature count.
The output is a structured plan covering anticipated actions for each preprocessing step, stored in memory and shown to the user as a brief plain-English summary. The plan is a guide not a contract — preprocessing agents deviate when evidence warrants it and every deviation is logged. Planning Mode 2 reads the actual preprocessing outcome, not this plan.
Phase - 3: Preprocessing
Step 1: Basic data cleaning
Code runs first: fixes type mismatches, removes exact duplicate rows, and flags structural invalids such as negative ages or percentages above 100. The code produces a cleaning report. The LLM then reads only the ambiguous findings — cases a rule cannot resolve — makes a provisional decision on each, and logs the reasoning. The LLM does not supervise mechanical cleaning.
Step 2: Exploratory data analysis
Code computes distribution shapes, a full correlation matrix, outlier flags using IQR and Z-score, missing value patterns, and per-feature correlation with the target. The LLM reads the full output and writes an insight narrative: most predictive features, distribution problems, target imbalance severity, near-redundant feature pairs, and domain observations inferrable from column names. This narrative is stored in memory and drives all downstream preprocessing decisions. A plain-English data summary is shown to the user.
Step 3: Feature selection
Code runs filter-based checks: variance thresholding, correlation thresholding for near-redundant pairs, and automatic flagging of likely identifier columns. The LLM makes the actual drop decisions using the EDA narrative and task config as context, reasoning about each flagged column in terms of the user's goal. Every drop decision is logged with a one-sentence rationale. The dataset state pointer is updated.
Step 4: Deep data cleaning
The LLM assigns a strategy to each remaining column with nulls — mean, median, mode, KNN, model-based imputation, or missingness flagging — based on the EDA narrative. It assigns an outlier treatment strategy per numeric column and an encoding strategy per categorical column, and determines whether scaling is needed and which method to apply. All assignments are logged before any code runs. Code executes all strategies in a single pass.
Step 5: Feature engineering
The LLM reads the cleaned dataset profile, EDA narrative, and task config and proposes candidate features — interaction terms, datetime decompositions, ratio features, or domain-inferred combinations. Each proposal is logged with a rationale. A leakage check runs in code before any feature is created. Features that fail are discarded and logged. The dataset profile in memory is updated to reflect the final feature set.
Verification agent
Code checks that no nulls remain, all features are correctly typed, dataset shape is consistent with expectations, and no feature has perfect correlation with the target. If any check fails the system routes back to the responsible step — not a full restart — with a maximum of two retries per step to prevent infinite loops. The LLM explains each failure and proposes a fix. All retries are logged. When all checks pass the final cleaned dataset is written to memory and the system proceeds.
Phase 4: Planning (Mode 2: Pipeline Execution Plan)
Input: task config + EDA narrative + final cleaned dataset profile + decisions log
Step 1 — Model family selection
The LLM reads the preprocessing outcomes — including any deviations from the Mode 1 plan — and reasons about which model families are appropriate. It considers dataset size, feature types and count, target distribution, class imbalance severity, and any user constraints from initialization. It notes where preprocessing deviated from the original plan and whether that changes the modelling approach. It produces a ranked shortlist of two to three model families with a plain-English justification for each.
Step 2 — Hyperparameter search and cross-validation strategy
The LLM specifies a search strategy per model family — random search for larger datasets, a small hand-reasoned grid for smaller ones, Bayesian optimization when computational budget allows. It determines the cross-validation strategy: stratified k-fold for classification, standard k-fold for regression, with fold count chosen relative to dataset size. It also defines what "good enough" performance means for this specific task — reasoning from the task context and user constraints rather than applying a fixed universal threshold.
Step 3 — Execution plan output
The agent produces a structured execution plan: ordered list of models, search strategy and parameter ranges for each, cross-validation design, evaluation metric, and the task-specific performance threshold. Stored in memory and passed to the execution phase.

Phase - 5: Execution
Step 1: Data splitting
Code splits the cleaned dataset into train and test sets using the strategy from the execution plan — stratified split for classification, standard for regression. The test set is held out entirely and never used during training or hyperparameter search. Split parameters are logged.
Step 2: Model training and evaluation
For each model in the execution plan, code trains using the specified cross-validation and hyperparameter search strategy. All models train on the same split under the same conditions for fair comparison. The LLM is not involved — this is pure code execution.
Results are collected into a comparison table: model name, cross-validation score, test set score, training time, and fold score variance as a stability indicator. The table is stored in memory and presented to the user in plain English.
Step 3: Result interpretation
The LLM reads the comparison table and writes a brief interpretation: best performing model, notable patterns such as a simpler model matching a complex one, high variance suggesting overfitting, or a large gap between cross-validation and test score suggesting leakage. This interpretation is added to the decisions log and shown to the user.
Phase - 6: Iterative Loop
Step 1: Threshold evaluation
Code checks whether the best model's test score meets the task-specific threshold defined in Planning Mode 2. If the threshold is met and the user is satisfied the loop does not activate and the system proceeds to final output. Maximum iteration count is three, enforced by the orchestrator.
Step 2: Failure diagnosis
If the threshold is not met the failure diagnosis agent activates. It reads the comparison table, decisions log, EDA narrative, and any error messages and categorizes the failure into one of four types: data quality issue, feature issue, model issue, or fundamental data insufficiency. For fundamental insufficiency the system exits the loop immediately and surfaces an honest plain-English explanation to the user rather than continuing to iterate pointlessly.
For the other three types the agent proposes a specific actionable fix and identifies which phase is responsible.
Step 3: Targeted revision and re-execution
The system returns to the specific responsible phase — not a full restart. A preprocessing issue reruns only the relevant step. A model issue re-invokes Planning Mode 2 with the failure diagnosis appended as additional context. After revision, execution reruns on the updated pipeline. New results are added to the comparison table alongside previous iteration results so improvement is visible. The iteration count increments and the loop repeats from Step 1.
Phase - 7: Final Output
Step 1: Explanation report
The LLM reads the complete decisions log and generates a final explanation report narrating the entire run in plain English: what the data looked like, every significant preprocessing decision and why it was made, which models were tried, how they performed, what the system changed when results were poor, and the final recommendation. This report is the primary explainability artifact — a non-expert user should be able to read it and understand exactly what was done and why.
Step 2: Final results presentation
The final comparison table is presented showing all models across all iterations, with the recommended model highlighted. The recommendation includes a plain-English justification grounded in the user's stated constraints from initialization — not just which model scored highest but why it is the right choice for this specific problem.
Step 3: Consolidated code output
The LLM reads all incremental code outputs produced during preprocessing and execution alongside the decisions log and generates one coherent, commented, end-to-end pipeline script — from raw data ingestion through preprocessing through final model training and prediction. Inline comments are tied directly to decisions log entries so every non-obvious line carries an explanation. The user can run this script independently of the system at any time.
Memory Mechanism
Episodic memory
The decisions log — an append-only timestamped record of every LLM decision, rationale, preprocessing action, model result, failure diagnosis, and revision within the current session. Created in initialization, written to continuously, and read by the failure diagnosis agent, the Planning Mode 2 agent, and the explanation report generator. It is the backbone of the system's explainability.
Semantic memory
Stores generalizable knowledge extracted from completed runs and retrieved in future runs to inform decisions. Updated only at the end of a fully completed successful run to prevent incomplete runs from polluting the knowledge base.
What is stored: associations between dataset profile characteristics and effective preprocessing strategies, associations between dataset profiles and model family performance, and associations between failure types and effective fixes.
What is retrieved and when: during Planning Mode 1 to inform preprocessing strategy, during Planning Mode 2 to inform model selection, and during failure diagnosis to surface fixes that resolved similar failures in past runs.
The retrieval mechanism is similarity-based — the current dataset profile is encoded as a feature vector and compared against stored profiles using cosine similarity. The most similar past experiences are surfaced as soft recommendations. The LLM then reasons about whether the retrieved knowledge applies to the current situation, keeping semantic memory advisory rather than deterministic.
